# Контракт синхронизации v1 — проект следующего этапа

Дата: 07.11.2026. Основание: `SPEC_SYNC.md`, `SPEC_ADMIN_PANEL.md` и последние решения владельца.
Это конкретный контракт для реализации и приёмки, **не описание уже работающего сервиса**.
Собственный сервер разрешён; GitHub Actions не использовать. Все проверки ниже — локально
или в доступном контейнере/на устройствах, без запуска workflow и автоматической публикации.

## 1. Объём и границы

Первая версия синхронизирует между Android API 26+ и Windows/Electron только профили,
сохранённые логины/пароли, избранное и заметки. Один аккаунт имеет одно активное хранилище
(vault); каждое устройство подключается отдельно. Браузер полноценно работает без аккаунта,
согласия на аналитику, сети или синхронизации. Синхронизация включается отдельным действием.

Не включать: cookies, живые входы на сайты, DOM/формы, вкладки, историю, файлы загрузок,
состояние инкогнито, локальные токены и согласие на аналитику. Хранение живых страниц
при переключении Android-профилей — отдельная задача управления GeckoSession.

Сервер знает аккаунт, устройства, идентификаторы хранилищ/записей, версии, удаления,
размеры и время обращений. Это необходимая метаинформация, **не полная анонимность**.
Тип записи, принадлежность профилю и содержимое шифруются на клиенте. Сервер не получает
ключ хранилища, открытые пароли сайтов, URL избранного или текст заметок.
Скомпрометированное разблокированное устройство находится за пределами защиты E2EE.
JWE защищает содержимое от чтения и подделки, но не гарантирует доступность и полноту
журнала злонамеренного сервера. Уже известную меньшую revision клиент отклоняет; новое
устройство без сохранённой контрольной точки не доказывает свежесть первого snapshot.
Не заявлять защиту от серверного rollback без отдельного проверенного механизма.

## 2. Идентификаторы и локальная миграция

Все межустройственные ID — UUIDv4 из системного CSPRNG, каноническая строка в нижнем
регистре `xxxxxxxx-xxxx-4xxx-yxxx-xxxxxxxxxxxx`. Генерация и проверка — стандартной библиотекой.

| Поле | Назначение |
|---|---|
| `accountId` | Сервер создаёт при регистрации; также служит идентификатором для входа |
| `vaultId` | Клиент создаёт для нового независимого хранилища |
| `deviceId` | Сервер создаёт для каждого подтверждённого подключения |
| `recordId` | Клиент создаёт один раз; одинаков при обновлении/удалении на всех устройствах |
| `profileId` | UUID профиля; совпадает с `recordId` его записи типа `profile` |
| `mutationId` | UUID одной неизменяемой попытки изменения; сохраняется до подтверждения |

Существующие числовые профили Android/Windows не переименовываются в UUID на месте.
Нужна локальная таблица `profile UUID ↔ local profile id`, привязанная к текущему аккаунту
и vault. `Gecko contextId("profile_N")`/Electron partition продолжают использовать локальный ID.
Два независимых «Профиля 1» на разных устройствах не объединяются по номеру или имени.

Миграция один раз присваивает UUID существующим заметкам, паролям и избранному и сохраняет
соответствие в транзакционном локальном хранилище. Миллисекунды и `os-$millis` не считаются
глобальными ID. Уже существующие UUID избранного можно сохранить после проверки формата
и уникальности. Текущий Android ID избранного имеет вид `b` + UUID: переносится проверенный
UUID после удаления только этого известного префикса, а исходный ID остаётся в таблице
соответствия. Произвольную строку GUID не обрезать и не считать UUID. Локальные ID интерфейса
допустимо оставить как отдельные ключи.

Чтение мигрируемого набора имеет три разных результата: `Empty`, `Loaded`, `Unreadable`.
Ошибка Keystore/DPAPI, повреждённый JSON или неподдерживаемая схема — `Unreadable`, не пустой
список. Сейчас `Passwords.list` в Android скрывает ошибку как `emptyList`; sync-миграция не
использует этот результат как доказательство отсутствия данных. Нужен отдельный строгий
read API с явной ошибкой. При `Unreadable` миграция/применение останавливаются, исходные
байты сохраняются, пользователю предлагается восстановление локального доступа. Никаких
outbox-удалений, tombstones, очистки vault или продвижения курсора на основании такой ошибки.

Первое подключение существующего устройства предлагает явный импорт локальных данных:
«объединить как отдельные записи» или «сначала скачать хранилище, локальные данные оставить
отдельно». Никакого скрытого удаления/перезаписи. Имя, URL или совпавший пароль не являются
доказательством общей идентичности; возможные дубликаты разбираются пользователем.

## 3. Расшифрованная схема записи

UTF-8 JSON, `schema: 1`, неизвестные обязательные версии отклоняются без перезаписи.
Общие поля: `recordId`, `kind`, `profileId` (UUID или `null`), `deleted` (boolean), `data`.
`kind` — только `profile`, `password`, `favorite`, `note`.
Все эти поля находятся **внутри JWE**, а не в открытом журнале сервера.

| `kind` | `profileId` | `data` живой записи |
|---|---|---|
| `profile` | Совпадает с `recordId` | Настраиваемые имя, описание, цвет, папка, закрепление, позиция |
| `password` | UUID существующего профиля | `origin`, `username`, `password`; canonical origin определён ниже |
| `favorite` | `null` | `title`, `url`, `folder` (имя, один уровень), позиция |
| `note` | `null` | `text`, необязательный исходный `url` |

### Canonical origin и применение паролей

`origin` пароля — ASCII-сериализация `scheme://host[:port]` без завершающего `/`, userinfo,
пути, query и fragment. Только `http`/`https`; scheme/имя DNS в нижнем регистре. Порт — число
1–65535 без ведущих нулей; `:80` для http и `:443` для https опускаются. Отличающийся от
стандартного порт сохраняется. DNS Unicode преобразуется UTS #46 nontransitional со STD3,
Bidi/ContextJ-проверками, затем валидируется; `faß.de` не превращается в `fass.de`.
Завершающая точка DNS сохраняется: не расширять origin автозаполнения неявным объединением.
IPv4 — канонические четыре десятичных октета, IPv6 — RFC 5952 в квадратных скобках;
zone ID запрещён. Не выполнять DNS-запросы при разборе/канонизации. Числовые сокращения,
hex/octal IPv4, userinfo, управляющие символы, пустой host и неоднозначные адреса отклоняются,
а не «исправляются» эвристически. Входной `origin` из sync должен уже совпадать с canonical
формой побайтово. При импорте локального полного URL сначала допустим разбор пути/query,
но результат origin проходит те же проверки; ошибочная запись сохраняется локально для разбора.

Обязательные общие примеры для Android/Windows:

| Локальный URL | Canonical origin |
|---|---|
| `HTTPS://ExAmPle.com:443/path?q=1#f` | `https://example.com` |
| `http://example.com:80/` | `http://example.com` |
| `https://example.com:8443/a` | `https://example.com:8443` |
| `https://faß.de/` | `https://xn--fa-hia.de` |
| `https://example.com./a` | `https://example.com.` |
| `http://127.0.0.1:8080/a` | `http://127.0.0.1:8080` |
| `https://[2001:0db8:0:0:0:0:0:1]:443/a` | `https://[2001:db8::1]` |
| `file:///a`, `https://u:p@example.com/`, `http://127.1/`, `http://0x7f000001/`, IPv6 zone ID | Ошибка |

Android `android.net.Uri` и `java.net.IDN` сами по себе не доказывают эту совместимость:
нужен строгий адаптер, например UTS #46 через доступный с API 24 `android.icu.text.IDNA`,
и общие положительные/отрицательные vectors с Windows URL/IDNA-адаптером. Ни один парсер
не выбирается без проверки заданных ограничений на обеих платформах.

Sync import/update адресует пароль **только по UUID записи и UUID профиля**. Текущий
`Passwords.upsert`, объединяющий по `origin+username` даже разные guid, для этого не подходит.
Нужен отдельный transactional `applyByRecordId`, сохраняющий разные UUID с одинаковыми
origin/username. Решение конфликта «сохранить обе» создаёт новый UUID и действительно две
записи; не проходит затем через старый dedup-upsert. Username/password не нормализуются
по регистру/Unicode и не служат идентификатором. Перед заполнением проверяется origin
активной страницы; sync-канонизация не расширяет существующие правила выдачи секретов.

Избранное и заметки в текущем приложении общие для профилей: v1 сохраняет эту семантику.
Пустые папки избранного в v1 не синхронизируются: это явное ограничение, не потеря записей.
Автоматически извлечённые из Gmail email/непрочитанное, последняя вкладка, язык интерфейса,
цвет локальной темы и состояние входа сайта не входят в запись профиля.
Строки вида `@ex_work_name` не отправлять как локализованный результат: сохранять
согласованный ключ шаблона либо явно введённое пользователем имя с отдельным признаком.

Для удаления `deleted: true`, `data: null`; ID и `kind` сохраняются. Зашифрованное содержимое
и открытый заголовок JWE должны согласовываться по ID, версии и признаку удаления.
Полученную ссылку применять только после локальной проверки разрешённых схем и полей.
Не загружать URL и не открывать заметки автоматически при получении данных.

Удаление профиля сначала атомарно публикует tombstone профиля. Получив его, клиент сразу
скрывает связанные пароли и прекращает их использование, даже если их очистка ещё идёт.
Затем связанные записи удаляются ограниченными CAS-пакетами; очередь очистки устойчива к сбою.
При создании/обновлении пароля запрос включает CAS-precondition живого профиля. Если профиль
удалили раньше, операция конфликтует; если пароль создали раньше, tombstone профиля скрывает
и эту запись. Сервер проверяет версии, а живой тип/связь проверяет клиент после расшифрования.
Старый клиент не воскрешает удалённый профиль ради сохранения пароля. Для применения snapshot
клиент сначала разрешает состояние профилей, затем связанные пароли; недостающая страница
профилей не считается доказательством удаления.

## 4. E2EE: стандартный формат и проверяемые зависимости

Не проектировать собственный PAKE, обмен Диффи—Хеллмана, подписи или формат шифра.
Использовать **JWE Compact Serialization (RFC 7516)** с `alg: "dir"`, `enc: "A256GCM"`.
Ключ хранилища — независимые случайные 32 байта из CSPRNG, не пароль аккаунта и не PIN.
Каждое шифрование использует новый случайный 96-битный IV и 128-битный GCM tag;
генерацию выполняет проверенная JOSE-библиотека. Повторное использование IV запрещено.

Защищённый заголовок JWE содержит:

```json
{"alg":"dir","enc":"A256GCM","typ":"os-sync+jwe","osv":1,
 "vault":"UUID","record":"UUID","rev":1,"epoch":1,"deleted":false}
```

Это описание формы, не готовый test vector. `UUID` заменяется валидным конкретным ID.
Заголовок целиком аутентифицируется стандартным JWE AAD; незашифрованные JWE headers,
`zip`, `jku`, `jwk`, `x5u`, произвольные `crit` и другие алгоритмы не принимать.
Проверяющий клиент сначала ограничивает размеры/алгоритмы, затем проверяет GCM tag,
затем сверяет `vault`, `record`, `rev`, `epoch`, `deleted` с ожидаемым контекстом операции.
Ни внешний JSON, ни серверный ответ не могут выбирать алгоритм или ключ произвольно.

Формат Compact: пять base64url-сегментов, пустой encrypted-key для `dir`:
`protected..iv.ciphertext.tag`. Сегменты без padding; JSON plaintext — UTF-8.
Не требуется самостоятельно канонизировать JSON: AAD — полученные защищённые байты JWE.
Любая ошибка тега/схемы/привязки блокирует применение записи и продвижение её курсора.
Содержимое ошибки не выводится в диагностику.

Кандидаты: поддерживаемая JOSE-библиотека `jose` на WebCrypto в Windows и поддерживаемая
JOSE/JCA-библиотека, например Nimbus JOSE+JWT, на Android. **Выбор конкретных версий ещё
не доказан**: перед реализацией проверить API 26, desugaring, зависимости, лицензию,
историю безопасности, зафиксировать версии и выполнить взаимные тесты. Не заменять
библиотеку самодельной AES-обвязкой ради прохождения сборки. Если выбранный Android
пакет несовместим, выбрать другой поддерживаемый стандартный JOSE-пакет и сохранить формат.

Android Keystore хранит локальный wrapping key; переносимый vault key сохраняется только
обёрнутым им, с отдельным назначением от текущего хранилища паролей. На Windows обёртка —
DPAPI через Electron `safeStorage` в главном процессе. Небезопасный fallback в открытый текст
запрещён. Веб-страницам, renderer/UI и preload не выдавать vault key. WebCrypto вызывается
из доверенного главного процесса/выделенного crypto worker, не из вкладки сайта.
Существующие Android ciphertext Keystore и Windows DPAPI не переносятся между устройствами:
клиент читает локальную запись и заново шифрует стандартным JWE.

## 5. Вход, устройства и перенос ключа без зависимости от SMTP

Минимальная v1 использует выданный `accountId` и пароль сервиса. Email, SMTP, социальный вход
и восстановление через письмо не требуются. Пароль передаётся только по HTTPS, не журналируется
и хранится на сервере как Argon2id-хеш с уникальной солью через поддерживаемую библиотеку.
Начальный ориентир — 64 MiB, 3 прохода, параллелизм 1; параметры измерить на сервере и сохранить
в PHC-строке, обеспечить ограничение конкурентных вычислений/попыток и миграцию параметров.
Это пароль сервиса; он не используется как ключ JWE и не совпадает автоматически с паролем сайта.

Серверные токены — случайные 256-битные opaque значения, в БД только SHA-256 токена.
Access token живёт до 15 минут в памяти клиента; refresh token до 30 дней хранится под защитой ОС,
ротируется при каждом подтверждённом использовании. Для ротации клиент **до отправки**
создаёт CSPRNG следующий refresh token и `rotationId` UUID, атомарно сохраняет старый токен,
следующий токен и неизменяемый запрос под защитой ОС. Сервер в одной транзакции проверяет
текущий хеш, сохраняет хеш нового токена и receipt с rotationId/хешем точных байтов запроса.
Клиент не генерирует следующий токен заново при сетевом повторе.

Точный повтор старого refresh с тем же rotationId/телом в течение 5 минут — безопасное
завершение той же ротации, **не сигнал к отзыву**. Сервер сверяет текущий хеш с уже принятым
следующим токеном и актуальность устройства; возвращает тот же статус/ID устройства и новый
короткоживущий access token. Access token можно перевыпустить: его открытое значение не
сохраняется в receipt, а refresh повторно не ротируется. Устройство сериализует refresh;
поздние ответы не заменяют более новое локальное состояние. Число access tokens ограничено.
После 5 минут клиент использует уже сохранённый следующий refresh: потеря ответа не требует
другого устройства или recovery. Если receipt показывает, что цепь уже продвинулась дальше,
повтор не откатывает её и возвращает `409 rotation_superseded`; клиент использует наиболее
новое сохранённое состояние. Старый токен с другим rotationId/телом — reuse и отзыв цепи.
Для точного повтора после окна возвращается `409 retry_expired`, без ложного отзыва устройства.
Хеши использованных токенов/rotationId сохраняются до истечения цепи, чтобы отличать это
от неизвестной скомпрометированной попытки; никаких открытых токенов в истории операций.
Каждый запрос проверяет актуальные account/device/session state в БД: отзыв действует немедленно,
а не через 15 минут. Bearer-токены не передаются в query/URL, журнал и тексты ошибок.

Вход одним паролем даёт только ограниченную сессию аккаунта: список обезличенных устройств,
создание запроса подключения, операции восстановления; доступа к vault ciphertext ещё нет.
Первое устройство регистрируется при создании аккаунта. Следующее требует подтверждения
существующим подключённым устройством **и отдельного прямого переноса ключа**:

1. Новое устройство входит в аккаунт и создаёт pending enrollment с одноразовым 256-битным
   секретом. Сервер хранит его хеш и ID запроса, срок 5 минут, без доступа к записям.
2. Новое устройство показывает QR с origin сервиса, ID запроса и одноразовым секретом.
   Уже подключённое устройство сканирует его; пользователь видит локально оба устройства
   и подтверждает конкретный запрос. Сервер атомарно принимает подтверждение от действующего
   устройства; один короткий числовой код без такого секрета недостаточен.
3. Подтверждающее устройство показывает **второй конфиденциальный QR/защищённый файл** для
   прямого импорта новым устройством: точный origin, accountId, vaultId, epoch, vault key,
   ID и секрет той же операции подключения. Пакет не загружается на сервер/в облако,
   не попадает в снимки приложения, журналы, буфер обмена или аналитику автоматически.
4. Новое устройство проверяет origin/аккаунт/ID запроса и оборачивает ключ средствами ОС.
   До запроса complete клиент генерирует и сохраняет под защитой ОС начальный refresh token,
   `completionId` UUID и неизменяемое тело запроса. Одноразовый секрет позволяет завершить
   только этот подтверждённый запрос. Сервер атомарно создаёт ровно один deviceId, сохраняет
   хеш начального refresh и completion receipt (ID/хеш тела/хеш enrollment-секрета), без
   открытых tokens. Точный повтор complete в течение 5 минут возвращает тот же deviceId
   и свежий access token, не создаёт устройство и не сбрасывает refresh-цепь. Отзыв устройства
   проверяется и перед таким ответом. Если initial refresh уже ротировался, complete возвращает
   `409 completion_superseded` без изменения tokens; если истекло окно — `409 retry_expired`.
   При потере любого ответа клиент уже знает initial refresh и может вызвать обычный refresh
   без знания server-generated deviceId; этот endpoint находит цепь по хешу токена и возвращает
   связанные accountId/deviceId. До передачи vault key новый refresh не используется для sync.
   Данные сервера не могут незаметно заменить ключ в отсканированном локальном пакете.

Передача QR — явный перенос секрета по физическому каналу, **не новый сетевой криптопротокол**.
Кто скопировал второй QR, получил ключ: интерфейс предупреждает об этом, скрывает QR при уходе
в фон и ограничивает показ временем. Автоматический удалённый обмен ключами не входит в v1;
для него нужен отдельный проверенный протокол с аутентификацией и анализом угроз.

Отзыв устройства отзывает все его сессии/токены, pending enrollments и новые запросы sync.
Уже скачанные/расшифрованные данные невозможно удалить дистанционно гарантированно.
Известный отозванному устройству общий vault key также нельзя «забыть» серверной командой.
При компрометации для криптографического исключения нужен новый vaultId и новый случайный ключ,
перешифрование текущих записей оставшимся устройством и повторное прямое подключение остальных.
Обычный отзыв гарантирует серверный запрет доступа; не обещать обратное шифрование старых копий.

## 6. Потеря пароля или ключа: явный набор восстановления

При создании аккаунта клиент предлагает сохранить локальный набор восстановления:
accountId, точный origin, vaultId, epoch, 32-байтовый vault key и **другой независимый**
256-битный одноразовый код восстановления аккаунта. Бинарные секреты кодируются base64url
стандартной библиотекой; пароль сервиса и токены устройств в набор не включаются.
Сервер получает лишь код восстановления аккаунта по TLS для сохранения его хеша,
но **никогда не получает vault key**. Набор может быть сохранён пользователем в файл/напечатан;
это секрет, дающий полный доступ, а не обычный экспорт настроек. До завершения onboarding
проверяется повторный импорт ключевых полей набора; отказ от сохранения допускается с явным
предупреждением о невосстановимости данных после потери всех устройств.

При наличии устройства можно сменить пароль с повторной проверкой текущего пароля либо
одноразовым кодом восстановления. При потере всех устройств код восстановления позволяет
сбросить пароль, отозвать все устройства и зарегистрировать новое. До запроса клиент генерирует
и сохраняет следующий случайный код восстановления; сервер атомарно погашает старый код и
сохраняет хеш нового. Поэтому потеря ответа не уничтожает последнюю копию нового кода. После
обрыва клиент проверяет вход с новым паролем; при необходимости повторяет восстановление
уже новым сохранённым кодом. Регистрация заменяющего устройства входит в ту же транзакцию;
утерянные при обрыве device tokens не восстанавливаются из открытого серверного журнала.
На клиенте отдельно импортируется vault key из офлайн-набора.

Один пароль аккаунта или его серверный сброс не расшифровывает старое хранилище.
Если нет ни vault key, ни действующего устройства, старые данные невосстановимы даже владельцем
сервера. Пользователь может явно начать новое пустое хранилище; старое удаляется отдельной
подтверждённой операцией, не скрыто при входе. Если потерян также код восстановления и все
устройства, восстановления аккаунта без SMTP/проверки личности в v1 нет: создаётся новый аккаунт.

## 7. Серверные версии, CAS и повторяемые операции

У каждой записи `revision` — положительное целое до `2^53-1`; у vault — монотонный `sequence`.
Sequence увеличивается **на каждое принятое change**, подряд в порядке changes пакета.
Пакет из N изменений атомарно получает N последовательных номеров; preconditions и точные
повторы mutationId номера не расходуют. При верхней границе sync/snapshot используется
только последний номер полностью закоммиченного пакета: верхняя граница не обрезает
транзакцию. Страницы могут делить большой пакет, но имеют одну верхнюю границу; клиент
применяет весь согласованный цикл атомарно после получения всех страниц.
Клиент отправляет полную замену записи, не операции над открытым содержимым:

```json
{"mutationId":"UUID","preconditions":[],"changes":[
  {"recordId":"UUID","baseRevision":0,"revision":1,"epoch":1,"deleted":false,"jwe":"..."}
]}
```

`baseRevision: 0` разрешён только для отсутствующего ID; обновление требует текущую ревизию,
`revision = baseRevision + 1`. `vaultId` берётся из пути, аккаунт/устройство — из проверенного
серверного контекста. Все изменения пакета либо принимаются одной БД-транзакцией, либо
отклоняются. `preconditions` содержит уникальные тройки `recordId/revision/deleted` для связанных
записей, которые не меняются, но должны оставаться на указанной версии/статусе удаления.
Для пароля это существующий профиль с `deleted: false`; одного совпадения revision недостаточно.
Preconditions относятся к состоянию БД **до** мутации, не к результату собственных changes.
Один ID не присутствует одновременно в changes и preconditions. Все проверки в одной транзакции.

Для минимальной v1 создание профиля и его первого пароля — **две транзакции**: сначала
подтверждённая живая запись профиля, затем пароль с precondition принятой revision/deleted=false.
Создать неизвестный профиль+пароль одним batch нельзя; клиентский scheduler сначала отправляет
зависимость. Для изменения самого профиля вместе с его паролями действует то же разбиение.
Удаление паролей при tombstone профиля не требует precondition живого профиля: иначе очистка
была бы заблокирована самим удалением. Создание/редактирование живого пароля его требует.
Сервер проверяет размеры, версии, ID, число записей и разрешённую форму JWE;
он не может подтвердить истинность зашифрованного содержимого и не объявляет её проверенной.

Idempotency key — `(accountId, vaultId, mutationId)`. Сервер хранит хеш точных байтов запроса
и результат в той же транзакции, что изменения. Повтор тех же байтов возвращает прежний результат
без счётчика новой синхронизации; тот же ID с другим телом — `409 mutation_mismatch`.
Проверка авторизации/отзыва выполняется **перед** возвратом результата повтора.
Принятые mutation receipts хранятся до удаления vault: это позволяет повторить неизвестный результат
после долгого офлайна. Их место учитывается в квоте; не удалять receipts по таймеру молча.
Клиент сохраняет неизменяемые JWE/IV/тело запроса до подтверждения, не шифрует повтор заново.

Операция даёт `409 conflict`, если CAS любой записи не совпал; остальные записи не меняются.
Ответ сообщает ID и текущие версии/ciphertext только уполномоченному устройству этого vault.
Отвергнутый конфликт не погашает mutationId; повторная операция после изменения тела получает новый ID.
Одновременный одинаковый повтор сериализуется БД, не проверкой только в памяти процесса.

## 8. Конфликты, офлайн и удаления

Не использовать клиентские часы для выбора победителя. Базовый алгоритм — трёхстороннее
сравнение расшифрованных `base/local/remote` на клиенте. Безопасно автоматически объединять
изменения разных записей и независимых полей одной записи. Если обе стороны изменили одно
поле по-разному, показать конфликт; не перезаписывать пароль или заметку по last-write-wins.
Пароль обрабатывается как цельная запись: автоматического смешивания username/password/origin нет.
Локальная конфликтующая версия остаётся в защищённой очереди до решения. Доступные решения:
оставить серверную, отправить локальную на новой CAS-версии или сохранить обе (новый UUID).

Удаление против редактирования — также конфликт; tombstone не исчезает от позднего офлайн PUT.
Tombstone в v1 терминален для своего UUID: повторное редактирование tombstone и undelete
того же ID запрещены. Восстановление возможно только явным действием пользователя как
новая живая запись с новым UUID; старый tombstone остаётся. Создание tombstone для ещё
не существующего серверного ID также запрещено. Локально созданная и удалённая до первой
подтверждённой отправки запись может быть исключена из outbox; при неизвестном результате
отправки сначала нужно выяснить его, а не предполагать отсутствие записи.
Зашифрованные tombstones хранятся весь срок жизни vault в v1, включая UUID уже удалённых записей:
это исключает автоматическое «воскрешение» устройством, которое было офлайн месяцами.

Локальная мутация данных и постановка outbox выполняются одной транзакцией. Текущие
разрозненные SharedPreferences/JSON требуют адаптера/транзакционного слоя; наблюдатель prefs
после записи не гарантирует отсутствие потерь при падении. Outbox шифруется на диске,
не содержит открытые пароли/заметки в служебных логах. Каждая запись имеет base snapshot,
baseRevision и локальную желаемую версию. Редактирование во время отправки создаёт следующую
локальную операцию и не меняет уже отправленные байты.

Курсор загрузки — серверный sequence с непрозрачной постраничной привязкой к vault/снимку.
Один sync-цикл фиксирует верхнюю границу sequence, скачивает все страницы до неё и применяет
данные с новым курсором атомарно. Повтор страницы безопасен. Сбой расшифрования не пропускает
запись и не портит локальную базу. Старый cursor ведёт к полному согласованному snapshot, который
включает tombstones. Поздние версии при полном snapshot не заменяются более старыми.

Запросы повторяются с ограниченным exponential backoff+jitter; `429` учитывает `Retry-After`.
`401` требует обновления токена/повторного входа; `403 device_revoked` прекращает фоновые попытки.
Без сети изменения остаются локально. Выход из аккаунта отменяет запросы, очищает токены,
закрывает текущий vault и не привязывает его очередь к другому аккаунту. Локальные данные
сохраняются или удаляются только по явному выбору пользователя, вне синхронизируемого удаления.

## 9. Минимальные API, квоты и хранение

Все `/v1/` endpoints — HTTPS, строгие schemas и ограничения тела до чтения в память.
Ниже контракт имён; существующий `server/src/admin.mjs` его пока не реализует.

| API | Требование |
|---|---|
| `POST /v1/accounts` | Регистрация первого устройства/пустого vault, без SMTP; защита от массовой регистрации |
| `POST /v1/auth/login`, `/refresh`, `/recover` | Раздельные ограниченные сессии/ротация/одноразовое восстановление |
| `POST /v1/enrollments`, `/{id}/approve`, `/{id}/complete` | Ограниченный pending flow; подтверждение действующим устройством |
| `GET /v1/devices`, `DELETE /v1/devices/{id}` | Только свой аккаунт; немедленный отзыв |
| `POST /v1/vaults/{id}/mutations` | Только подтверждённое устройство; CAS, транзакция, idempotency |
| `GET /v1/vaults/{id}/changes` | Курсор/верхняя граница/пагинация, только свой vault |
| `DELETE /v1/account` | Повторная проверка пароля либо recovery-кода; немедленный отзыв и удаление |

### Малый v1: лимиты и обеспеченное место для удаления

Это конкретные стартовые admission-лимиты малого сервиса, а не обещание разместить
100 000 записей по 256 KiB. Большие прежние ориентиры этим разделом заменены.

| Ограничение | Значение v1 |
|---|---|
| Устройства аккаунта | 10 |
| ID записей аккаунта, включая терминальные tombstones | 4 096 |
| ID записей всей установки | 16 384 |
| Основной charged-бюджет аккаунта | 100 MiB |
| Основной charged-бюджет всей установки | 256 MiB |
| Резерв аккаунта под конечные удаления | 16 MiB |
| Резерв всей установки под конечные удаления | 64 MiB |
| `maxLiveJweBytes` | 256 KiB |
| `maxTombstoneJweBytes` | **2 048 байт** полного UTF-8 Compact JWE |
| Изменения одного пакета / размер тела | 100 / 1 MiB |
| Страница ответа | До 100 записей / 1 MiB |
| Частота sync устройства | 60 запросов в минуту |

Tombstone содержит только служебные ID/kind/profileId/deleted/data:null, без пользовательского
текста; это позволяет обеим реализациям укладываться в 2 048 байт. Соответствующий interop-vector
и проверки размера нужны **до** включения записи живых данных. Удаление не должно требовать
повторной отправки прежнего большого ciphertext. Максимум live JWE не распространяется
на tombstones: oversized tombstone отклоняется без расходования резерва.

При admission **каждого нового recordId** транзакция отдельно бронирует 4 096 charged-байт:
2 048 для конечного JWE, 512 для его доли delete receipt и 1 536 для записи версии/индексов/
указателя current. Это бухгалтерский резерв, не физическое предвыделение файла. Сумма
забронированного, включая уже израсходованное, должна помещаться одновременно в account
и global reserve. Даже tiny live запись нельзя принять без её полного резерва. Для
4 096 ID это ровно 16 MiB на аккаунт; глобальные 16 384 ID требуют не более 64 MiB.

Резерв расходуется только при **первом live→tombstone** этого ID, с его receipt и version
metadata. Обычные PUT, повторные tombstone edits, новые ID и undelete не используют его.
Точный повтор delete по mutationId не расходует место/sequence повторно. Receipt удаления
может содержать только ограниченные ID/revision/sequence/result, без запросов/JWE; его
charged-размер не превышает 512 байт на удаляемый ID (бюджет пакета суммируется по ID).
После tombstone остаток резерва не возвращается обычным PUT: ID остаётся терминальным.
Удаление аккаунта/vault освобождает его логические квоты и не требует свободной квоты.

Все live версии immutable journal, current state, mutation receipts и любые сохраняемые
snapshot-копии учитываются в основном charged-бюджете по фактически сохраняемым UTF-8
байтам JWE/receipt плюс фиксированные metadata allowances схемы. Не считать только
последнюю версию: update не освобождает место удерживаемой истории. Current хранит ссылку
на единственную immutable version, а не вторую неучтённую копию JWE. Стабильный snapshot
по upper sequence по возможности является запросом к этому журналу; если материализуются
дополнительные копии/страницы, они также charged. В v1 не предполагается неограниченная
история за пределами квоты. Нормальная квота может исчерпаться раньше максимума ID.

Ни одна мутация не допускается на основе счётчика из памяти: admission, charges, резерв,
CAS/preconditions, journal и receipt изменяются одной БД-транзакцией. Пакет проверяет
итоговый account/global размер; частичной записи нет. Смешанный live/delete пакет при
полной обычной квоте может быть отклонён целиком; клиент тогда отправляет delete-only
пакеты отдельно, сохраняя их атомарность. Предусмотренный reserve гарантирует **логическое
разрешение** конечных удалений при полной обычной квоте, но не исправность диска или VPS.

Charged-учёт не является точным размером SQLite: страницы, WAL, vacuum, шифрование backups
и параллельные запросы требуют отдельного эксплуатационного запаса. Перед реальной
выкладкой измерить worst-case БД/WAL/backup на этих пределах; admission новых данных
останавливается при недостаточном свободном месте/нарушенной storage health раньше квоты.
Не обещать возможность заполнить логические лимиты на неподтверждённом VPS. Ошибка диска
не превращает удаление в успех: возвращается явная ошибка, клиент хранит операцию для повтора.

API не разрывает запись размером 256 KiB на куски; меньшая страница допустима.
`413` — размер, `429` — частота, `409 quota_exceeded` — логическое хранилище;
никаких частичных импортов без отчёта и автоматической очистки пользовательских данных.
Удаление большого профиля сначала атомарно публикует tombstone профиля, сразу скрывающий
связанные пароли, затем отправляет ограниченные delete-only пакеты очистки по их UUID.
CAS-precondition профиля блокирует новые живые пароли после его tombstone; очередь очистки
устойчива к сбою и повтору. Логическая атомарность скрытия профиля не означает один гигантский
пакет всех его паролей. Состояние незавершённой физической очистки видно пользователю.

Живые записи и tombstones хранятся до явного удаления vault/аккаунта; не вводить скрытый срок
неактивности. Подтверждённое удаление сразу запрещает доступ, удаляет рабочие данные и токены;
резервные копии имеют ограниченный срок 30 суток. До запуска проверить реальную ротацию,
восстановление и запрет возвращения удалённого аккаунта из backup (журнал удалений отдельно
от восстанавливаемого snapshot, без содержимого vault). Свойства восстановления/очистки
нельзя обещать, пока они не доказаны на выбранном VPS.

Ограничители частоты могут хранить IP только временно в памяти. Reverse proxy, application logs,
HTTP/error dumps не сохраняют IP, Authorization, cookie, тела запросов, JWE или recovery-пакеты.
Это запрет логирования запросов, **не запрет необходимых ciphertext в резервной копии БД**.
Резервная копия БД может содержать JWE записей, tombstones, версии/ID, mutation receipts и
хеши проверочных секретов — под отдельным серверным backup-шифрованием и контролем доступа,
с указанным сроком 30 суток. Она никогда не содержит открытые vault keys, пароли сайтов,
recovery-наборы, access/refresh tokens или иные открытые auth secrets. После восстановления
принудительно отзываются сессии и неприменённые enrollment/refresh receipts; старое состояние
не должно оживлять ранее отозванные устройства/коды. Продуктовая аналитика и технические
метрики не используют запросы как журнал действий.

## 10. Панель владельца и отдельное согласие на аналитику

Owner auth `/admin/` отделена от обычной account/device auth. Роль владельца не даёт токен
обычного пользователя, ключ JWE или API для чтения его расшифрованных записей. Личный vault
владельца — обычный аккаунт. Панель получает только сводки числа аккаунтов/устройств,
размера ciphertext, успешных/неуспешных sync-операций и состояния сервиса; неподключённые
метрики обозначаются отсутствием данных, а не нулём. Не добавлять просмотр содержимого vault.

Аналитика функций не является условием входа, регистрации или sync. Согласие хранится
отдельно для `(accountId, deviceId, consentVersion)` и **не входит в синхронизируемые записи**.
Новое устройство, другой аккаунт, переустановка без доказанного локального состояния — выключено.
Выход из аккаунта/отзыв согласия отменяет analytics transport, очищает неотправленную очередь
и не отправляет прежние счётчики после нового входа. Инкогнито не собирается.

Будущий analytics endpoint проверяет действующий device token и актуальное отдельное согласие
на сервере; `consent: true` из JSON не считается разрешением. Отправляются только allowlist
функций/платформа/сводные счётчики из `usage-schema.mjs`. Ни accountId/deviceId, ни vault ID,
ни URL, ни имена/пароли/тексты не сохраняются в аналитических агрегатах. Контекст авторизации
используется кратковременно для проверки/порога участников и не становится идентификатором события.

Подтверждение доставки analytics должно проектироваться отдельно: нынешний `UsageQueue.drain()`
не реализует сетевые ack/retry. Согласие нужно перепроверять перед фактической отправкой;
отзыв побеждает уже подготовленную, но не отправленную очередь. Агрегаты сохраняют пороги
малых групп и срок 30 дней по `SPEC_ADMIN_PANEL.md`; незавершённость sync не оправдывает
публичный сборщик без проверенной авторизации/согласия.

## 11. Обязательные доказательства перед готовностью

- Межплатформенные JWE test vectors Android→Windows и Windows→Android: UTF-8/арабский/эмодзи,
  пустые и предельные поля, разные JSON headers, полный 128-битный tag. Отдельно негативные
  проверки изменения IV/tag/header/vaultId/recordId/revision, неверного ключа/алгоритма/размера.
- На реальном API 26 и актуальном Android: Keystore wrapping/unwrapping переносимого ключа,
  перезапуск, блокировка устройства, потеря ключа/переустановка. На Windows — DPAPI под другим
  пользователем/машиной не раскрывает ключ; portable ZIP не превращает ключ в переносимый plaintext.
- Два устройства, два аккаунта, одинаковые локальные номера профилей: двусторонний обмен четырьмя
  типами, без смешения профилей. Явный импорт, офлайн, разрыв ответа после commit, повтор mutationId,
  CAS-конфликт, удаление/редактирование, конкурентное удаление профиля/создание пароля;
  создание профиля+пароля через две подтверждённые транзакции и отказ live-precondition на tombstone.
- Canonical origin vectors (IDNA/IPv6/порты/точка DNS), сохранение обеих password-записей с
  одинаковыми origin/username и разными UUID; Keystore/JSON failure не порождает пустой sync или delete.
- Подключение требует подтверждения, одноразовый enrollment не переиспользуется; чужой аккаунт,
  отозванное устройство, неподтверждённый pending и переигранный recovery отклоняются.
  Разрыв ответа после refresh/complete commit, точные повторы до/после окна, конкурирующие
  ротации и поздние ответы не отзывают легитимное устройство и не восстанавливают старую цепь.
  Повтор с изменённым телом и реальное reuse старого refresh проверяются отдельно.
- Потеря пароля при сохранённом ключе/коде; потеря ключа при известном пароле; потеря всех устройств;
  удаление аккаунта и восстановление backup без возвращения удалённого. Повторы recovery после обрыва.
- Границы account/global main quota и зарезервированного admission, 2 048-байтный tombstone,
  конечное удаление после заполнения обычной квоты, oversized tombstone без утраты резерва,
  exact delete retry и mixed-пакеты; история/snapshot не обходят charged-квоту; concurrent
  admissions не превышают предел. При исчерпании диска нет ложного подтверждения удаления.
- Сетевой/БД/лог-аудит без открытых секретов/контента. Сверка реальных метрик панели с транзакциями.
  Отказ/отзыв/другой аккаунт/новое устройство/инкогнито не отправляют аналитику.
- Все новые строки сразу на 16 языках по GLOSSARY.md, арабский RTL; политика и материалы магазина
  описывают реальные сроки/метаданные/невосстановимость ключа до включения сервиса.

Текущие блокеры: нет account/device/sync API и схемы БД, транзакционных клиентских outbox/UUID-миграций,
JOSE interop-доказательств, UI подключения/восстановления/согласия, реального metrics adapter и подтверждённой
HTTPS/backup-эксплуатации VPS. Порядок: совместимые криптофикстуры и модель данных → серверные транзакции/
авторизация → клиентские миграции и offline sync → два устройства/восстановление → согласие и метрики →
эксплуатационная приёмка. До прохождения этих пунктов синхронизация остаётся проектом, не доступной функцией.
